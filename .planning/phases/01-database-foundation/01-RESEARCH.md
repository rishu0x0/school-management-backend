## Summary

Phase 1 is purely a Supabase schema phase: create 7 tables, all indexes, all constraints, all RLS policies, and validate the full setup via `supabase db reset`. No Go code, no Flutter code. The output is a `supabase/migrations/` directory with SQL files that produce a clean, reproducible schema on any fresh Supabase project.

The most important technical decision for this phase is the RLS architecture. The Go backend connects with the **service role key**, which bypasses RLS entirely — RLS here is defense-in-depth, not the primary auth layer. This means RLS policies must still be written correctly (they protect against Supabase dashboard access, direct PostgREST queries, and future mistakes), but the Go API's WHERE clauses are the authoritative ownership enforcement. The two-teacher isolation test verifies RLS works correctly for direct DB access.

The second key concern is performance: every policy column that appears in a USING clause needs a B-tree index, and all `auth.uid()` calls should be wrapped in `(select auth.uid())` to trigger PostgreSQL's initPlan optimization. Supabase's own documentation shows this pattern yields 94–99% query time improvements. Since the ownership chain for `attendance_records` requires a two-level subquery through `attendance_sessions`, this optimization is critical.

**Primary recommendation:** Write all DDL (tables, constraints, indexes) in one migration file and RLS policies in a second migration file. Use `supabase migration new` for each, commit both to git, and validate with `supabase db reset` before declaring the phase done.

## Architecture Patterns

### Migration File Structure

```
supabase/
├── config.toml          # Supabase CLI project config (auto-generated by supabase init)
├── migrations/
│   ├── 20260519000001_create_schema.sql     # All tables, constraints, indexes
│   ├── 20260519000002_rls_policies.sql      # All RLS ENABLE + CREATE POLICY statements
│   └── 20260519000003_triggers.sql          # Midnight lock trigger (defense-in-depth)
└── seed.sql             # Two test teachers + sample class + sample students
```

**Rule:** Never manually rename migration files after they are applied. Supabase CLI applies them in timestamp order; renaming breaks the history.

### Pattern 1: Single-File DDL Migration

**What:** All `CREATE TABLE`, `UNIQUE`, `CHECK`, and `CREATE INDEX` statements for all 7 tables in one migration file.
**When to use:** Phase 1 initial schema — everything is new, no incremental changes yet.

```sql
-- Source: supabase.com/docs/guides/deployment/database-migrations
-- Migration: 20260519000001_create_schema.sql

-- Enable UUID generation
CREATE EXTENSION IF NOT EXISTS "pgcrypto";

-- teachers
CREATE TABLE teachers (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name          TEXT NOT NULL,
  mobile        TEXT UNIQUE NOT NULL,
  school_name   TEXT NOT NULL,
  password_hash TEXT NOT NULL,
  is_verified   BOOLEAN DEFAULT FALSE,
  created_at    TIMESTAMPTZ DEFAULT NOW()
);

-- refresh_tokens
CREATE TABLE refresh_tokens (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  teacher_id   UUID NOT NULL REFERENCES teachers(id) ON DELETE CASCADE,
  token_hash   TEXT NOT NULL,
  device_hint  TEXT,
  last_used_at TIMESTAMPTZ,
  created_at   TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX ON refresh_tokens(teacher_id);
CREATE INDEX ON refresh_tokens(token_hash);  -- critical: token lookup on every /auth/refresh

-- classes
CREATE TABLE classes (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  teacher_id UUID NOT NULL REFERENCES teachers(id) ON DELETE CASCADE,
  name       TEXT NOT NULL,
  section    TEXT,
  subject    TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(teacher_id, name)
);
CREATE INDEX ON classes(teacher_id);

-- students
CREATE TABLE students (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  class_id    UUID NOT NULL REFERENCES classes(id) ON DELETE CASCADE,
  roll_number INTEGER NOT NULL,
  full_name   TEXT NOT NULL,
  photo_url   TEXT,
  is_active   BOOLEAN DEFAULT TRUE,
  created_at  TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(class_id, roll_number)
);
CREATE INDEX ON students(class_id);

-- attendance_sessions
CREATE TABLE attendance_sessions (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  class_id     UUID NOT NULL REFERENCES classes(id),
  teacher_id   UUID NOT NULL REFERENCES teachers(id),
  date         DATE NOT NULL,
  submitted_at TIMESTAMPTZ,
  is_locked    BOOLEAN DEFAULT FALSE,
  created_at   TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(class_id, date)
);
CREATE INDEX ON attendance_sessions(class_id);
CREATE INDEX ON attendance_sessions(teacher_id);
CREATE INDEX ON attendance_sessions(class_id, date);  -- covers the UNIQUE constraint but also range queries

-- attendance_records
CREATE TABLE attendance_records (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  session_id UUID NOT NULL REFERENCES attendance_sessions(id) ON DELETE CASCADE,
  student_id UUID NOT NULL REFERENCES students(id),
  status     TEXT NOT NULL CHECK (status IN ('present', 'absent', 'leave')),
  marked_at  TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ,
  UNIQUE(session_id, student_id)
);
CREATE INDEX ON attendance_records(session_id);
CREATE INDEX ON attendance_records(student_id);

-- generated_reports
CREATE TABLE generated_reports (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  class_id     UUID NOT NULL REFERENCES classes(id),
  teacher_id   UUID NOT NULL REFERENCES teachers(id),
  month        DATE NOT NULL,
  file_type    TEXT NOT NULL CHECK (file_type IN ('pdf', 'excel')),
  file_url     TEXT NOT NULL,
  generated_at TIMESTAMPTZ DEFAULT NOW(),
  expires_at   TIMESTAMPTZ,
  UNIQUE(class_id, month, file_type)  -- prevents duplicate report generation (idempotency)
);
CREATE INDEX ON generated_reports(teacher_id);
CREATE INDEX ON generated_reports(class_id, month);
CREATE INDEX ON generated_reports(expires_at);  -- cleanup cron queries this
```

### Pattern 2: Separate RLS Migration

**What:** All `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` and `CREATE POLICY` statements in a dedicated migration file, separate from DDL.
**When to use:** Always — keeps security concerns clearly separated, easy to audit.

```sql
-- Source: supabase.com/docs/guides/database/postgres/row-level-security
-- Migration: 20260519000002_rls_policies.sql

-- Enable RLS on all tables
ALTER TABLE teachers ENABLE ROW LEVEL SECURITY;
ALTER TABLE refresh_tokens ENABLE ROW LEVEL SECURITY;
ALTER TABLE classes ENABLE ROW LEVEL SECURITY;
ALTER TABLE students ENABLE ROW LEVEL SECURITY;
ALTER TABLE attendance_sessions ENABLE ROW LEVEL SECURITY;
ALTER TABLE attendance_records ENABLE ROW LEVEL SECURITY;
ALTER TABLE generated_reports ENABLE ROW LEVEL SECURITY;

-- IMPORTANT: The Go backend uses the SERVICE ROLE KEY which bypasses RLS.
-- These policies apply to:
--   (a) Supabase Dashboard access
--   (b) Direct PostgREST (anon key) queries
--   (c) Any future code that uses a non-service-role key
-- 
-- Performance note: wrap auth.uid() in (select auth.uid()) to enable
-- PostgreSQL initPlan caching — 94-99% query time improvement per Supabase docs.

-- teachers: each teacher can only see/edit their own row
CREATE POLICY "teacher_can_manage_own_row" ON teachers
  FOR ALL
  TO authenticated
  USING ((select auth.uid()) = id);

-- refresh_tokens: teacher sees only their own tokens
CREATE POLICY "teacher_owns_refresh_tokens" ON refresh_tokens
  FOR ALL
  TO authenticated
  USING (teacher_id = (select auth.uid()));

-- classes: teacher sees only their own classes
CREATE POLICY "teacher_owns_classes" ON classes
  FOR ALL
  TO authenticated
  USING (teacher_id = (select auth.uid()));

-- students: teacher sees students in classes they own
-- Uses subquery pattern (NOT a join) for performance
CREATE POLICY "teacher_owns_students" ON students
  FOR ALL
  TO authenticated
  USING (
    class_id IN (
      SELECT id FROM classes
      WHERE teacher_id = (select auth.uid())
    )
  );

-- attendance_sessions: teacher owns sessions directly (teacher_id FK)
CREATE POLICY "teacher_owns_sessions" ON attendance_sessions
  FOR ALL
  TO authenticated
  USING (teacher_id = (select auth.uid()));

-- attendance_records: two-level chain — session → teacher
-- Note: session_id index on attendance_records makes this subquery fast
CREATE POLICY "teacher_owns_attendance_records" ON attendance_records
  FOR ALL
  TO authenticated
  USING (
    session_id IN (
      SELECT id FROM attendance_sessions
      WHERE teacher_id = (select auth.uid())
    )
  );

-- generated_reports: direct teacher_id FK
CREATE POLICY "teacher_owns_reports" ON generated_reports
  FOR ALL
  TO authenticated
  USING (teacher_id = (select auth.uid()));
```

### Pattern 3: Midnight Lock DB Trigger (Defense-in-Depth)

**What:** A PostgreSQL trigger that prevents UPDATE on `attendance_records` if the session date has passed midnight.
**When to use:** After RLS policies, as a third layer of protection.

```sql
-- Migration: 20260519000003_triggers.sql

-- Midnight lock: rejects edits to attendance records after midnight UTC of the session date
-- Primary enforcement is in the Go API; this is defense-in-depth
CREATE OR REPLACE FUNCTION check_attendance_not_locked()
RETURNS TRIGGER AS $$
BEGIN
  -- Check if the session is explicitly locked
  IF EXISTS (
    SELECT 1 FROM attendance_sessions
    WHERE id = NEW.session_id AND is_locked = TRUE
  ) THEN
    RAISE EXCEPTION 'attendance_locked'
      USING DETAIL = 'This attendance session is locked and cannot be modified.';
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER attendance_record_lock_check
  BEFORE UPDATE ON attendance_records
  FOR EACH ROW EXECUTE FUNCTION check_attendance_not_locked();

-- Also prevent direct updates to locked sessions
CREATE OR REPLACE FUNCTION check_session_not_locked()
RETURNS TRIGGER AS $$
BEGIN
  IF OLD.is_locked = TRUE THEN
    RAISE EXCEPTION 'attendance_locked'
      USING DETAIL = 'This attendance session is already locked.';
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER attendance_session_lock_check
  BEFORE UPDATE ON attendance_sessions
  FOR EACH ROW EXECUTE FUNCTION check_session_not_locked();
```

### Anti-Patterns to Avoid

- **Making schema changes via Supabase Dashboard on the remote DB:** This bypasses migration history and causes `supabase db push` to fail with sync errors. All changes must go through migration files.
- **Writing RLS policies inside the same migration as DDL:** Harder to audit security. Keep DDL and RLS in separate migration files.
- **Using `auth.uid()` without `(select auth.uid())` wrapper:** PostgreSQL calls `auth.uid()` once per row without the wrapper. The `(select ...)` wrapper triggers initPlan caching. Supabase docs show 94% query time improvement.
- **Subquery with JOIN vs IN subquery:** `auth.uid() IN (SELECT user_id FROM team WHERE team.id = table.team_id)` is much slower than `team_id IN (SELECT team_id FROM team WHERE user_id = auth.uid())`. Always put `auth.uid()` in the inner query.
- **Missing index on `token_hash` in `refresh_tokens`:** The Go backend performs `SELECT * FROM refresh_tokens WHERE token_hash = $1` on every API request that uses a refresh token. Without an index this is a full table scan.
- **Missing `UNIQUE(class_id, month, file_type)` on `generated_reports`:** Without this, the cron job can produce duplicate report rows if the server restarts on the 1st of the month.
- **Storing signed URLs in `generated_reports.file_url`:** Signed URLs expire. Store the Supabase Storage object path instead and generate fresh signed URLs on each download request.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Migration versioning | Custom SQL runner script | `supabase migration new` + `supabase db reset` | CLI handles ordering, history tracking, and idempotent replay |
| UUID generation | Custom application-layer UUID | `gen_random_uuid()` in PostgreSQL | Cryptographically random, no application round-trip, consistent across all inserts |
| Row ownership enforcement | Application-level ownership middleware only | PostgreSQL RLS policies | Defense-in-depth; RLS fires at the DB level even if application logic has bugs |
| Timestamp defaults | Application sets `created_at` in Go | `DEFAULT NOW()` in PostgreSQL | Server-side timestamp is authoritative; no clock skew from application |
| Cascade delete logic | Application-layer delete orchestration | `ON DELETE CASCADE` on foreign keys | Guaranteed atomicity; no orphan rows even if application crashes mid-delete |

**Key insight:** PostgreSQL (via Supabase) handles everything in this phase natively. The entire phase is SQL — no application code needed.

## Common Pitfalls

### Pitfall 1: RLS Policies That Use `auth.uid()` Without the SELECT Wrapper

**What goes wrong:** RLS policy written as `USING (teacher_id = auth.uid())` — PostgreSQL calls `auth.uid()` for every row being evaluated, making the policy O(n) in table size.
**Why it happens:** Default copy-paste from basic tutorials that predate the performance guidance.
**How to avoid:** Always write `USING (teacher_id = (select auth.uid()))`. The `(select ...)` wrapper causes PostgreSQL to evaluate `auth.uid()` once per query (initPlan) and cache the result.
**Warning signs:** Slow queries on attendance_records or students tables as data grows; Supabase dashboard performance advisor flags "auth_rls_initplan" lint warning.

### Pitfall 2: Missing Index on Ownership-Chain Subquery Column

**What goes wrong:** The `attendance_records` RLS policy uses `session_id IN (SELECT id FROM attendance_sessions WHERE teacher_id = ...)`. If `attendance_sessions.teacher_id` has no index, this subquery scans the entire sessions table on every row evaluation.
**Why it happens:** Indexes are added for application query performance but developers forget RLS subqueries also run against the same tables.
**How to avoid:** Every column that appears in a RLS policy's USING clause (directly or in a subquery) needs a B-tree index. In this schema: `classes(teacher_id)`, `attendance_sessions(teacher_id)`, `refresh_tokens(teacher_id)`, `generated_reports(teacher_id)`.
**Warning signs:** Supabase dashboard advisors flag unindexed foreign keys; slow reads on child tables.

### Pitfall 3: Two Different Teachers Can See Each Other's Data if RLS Not Tested

**What goes wrong:** RLS policies are written but never tested with two distinct teacher identities. A subtle policy mistake (e.g., wrong column reference, wrong table alias) silently returns empty results instead of the correct rows — or returns ALL rows.
**Why it happens:** Single-teacher development testing never exercises the isolation guarantee.
**How to avoid:** Create two teacher rows in the test data. Use Supabase Dashboard SQL Editor to run `SET LOCAL role = authenticated; SET LOCAL request.jwt.claims = '{"sub": "<teacher_1_id>"}'` and verify Teacher 1 cannot see Teacher 2's classes.
**Warning signs:** RLS is enabled (green lock icon in Supabase dashboard) but policy list shows 0 policies on a table — rows are inaccessible to ALL users including legitimate ones.

### Pitfall 4: `supabase db reset` Fails Because Migration Has Errors

**What goes wrong:** `supabase db reset` replays all migrations from scratch. A typo or constraint violation in any migration file causes the entire reset to fail with an unhelpful error.
**Why it happens:** Migration files are written incrementally and not tested against a clean database until reset time.
**How to avoid:** Run `supabase db reset` after writing EACH migration file, not only at the end. This catches errors at the migration they were introduced, not at the end when all files run together.
**Warning signs:** `ERROR: relation "X" does not exist` — a migration references a table created in a later-timestamped migration.

### Pitfall 5: service_role Key Bypasses RLS — Anon Key Does Not

**What goes wrong:** Developer writes RLS policies, tests via Supabase Dashboard (which uses service_role) and concludes "RLS is working." In reality, the service_role key bypasses all RLS policies. The anon key enforces them. The Go backend uses service_role (correct, intentional), but any test that uses service_role to verify RLS behavior gives false positives.
**Why it happens:** Supabase Dashboard and service_role key appear to be "admin access" but the exact RLS bypass behavior is not obvious.
**How to avoid:** Test RLS specifically using the anon key with a simulated JWT. Use Supabase's RLS testing capability in the SQL editor or the Supabase CLI's `--anon` mode. The phase success criterion requires testing "as two different teacher IDs" — this must use a non-service-role key.

### Pitfall 6: `refresh_tokens.token_hash` Has No Index

**What goes wrong:** Every call to `/api/v1/auth/refresh` does `SELECT * FROM refresh_tokens WHERE token_hash = $1`. Without an index on `token_hash`, this is a full table scan. With 1,000 active device sessions, this is negligible. With 10,000+ teachers each with multiple devices, this becomes the bottleneck for every authenticated API request.
**Why it happens:** `token_hash` is not a foreign key (so it gets no automatic index) and is not the primary key.
**How to avoid:** Add `CREATE INDEX ON refresh_tokens(token_hash)` in the DDL migration. This is included in the code example above.

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|

## Open Questions

1. **IST vs UTC for `is_locked` flag and trigger**
   - What we know: The attendance lock fires at "midnight" — the question is midnight in which timezone. Server will run in UTC. Teachers are in IST (UTC+5:30).
   - What's unclear: The DB trigger as written checks `is_locked = TRUE` — the flag must be set by the Go API using IST-aware logic. The trigger itself is stateless on timezone.
   - Recommendation: The trigger only checks the `is_locked` boolean (set by Go API with IST logic). Do NOT put timezone math in the SQL trigger — that complexity belongs in Go. Document this clearly in the migration file comment.

2. **Whether to use Supabase Auth UIDs or custom teacher UUIDs for `auth.uid()` in RLS**
   - What we know: This project uses custom JWTs issued by the Go backend, not Supabase Auth. `auth.uid()` returns the `sub` claim from the JWT. For RLS to work with the anon key + custom JWT, Supabase must be configured to verify JWTs signed by the Go backend's secret.
   - What's unclear: Whether Supabase's "JWT secret" configuration (in `config.toml`) needs to match the Go backend's `JWT_SECRET` env var.
   - Recommendation: In Phase 1, RLS is defense-in-depth only (Go uses service role key). The `auth.uid()` policies are written for future correctness. The two-teacher isolation test should use service role to insert and verify schema, and manually verify policy syntax with Supabase's policy tester. Full anon-key RLS testing with custom JWTs belongs in Phase 2 when the Go JWT is implemented.

3. **Connection pooler vs direct connection for Go backend**
   - What we know: Supabase provides two connection strings: direct (port 5432) and PgBouncer pooler (port 6543). `pgxpool` in Go manages its own connection pool.
   - What's unclear: Free tier connection limits (typically 60 direct connections on free/Pro Supabase).
   - Recommendation: Use the direct connection string (port 5432) for the Go API with `pgxpool` set to `MaxConns: 10`. Use PgBouncer only if connection limit is hit. Document which connection string is in `.env`.
